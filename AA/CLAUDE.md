# AA (asset-allocation smallcases): project rules

The research framework is [`../AGENT.md`](../AGENT.md). Copy [`../TEST_TEMPLATE.md`](../TEST_TEMPLATE.md) for every new test.

- **Data boundary (read first; standing rule, 2026-11-06).** The only data you may read is what [`data/APPROVED_DATA.md`](data/APPROVED_DATA.md) lists as `APPROVED`. It gives each file's path and through-date and the latest usable date per role. Everything else on disk is off-limits: newer-looking files, `PENDING` and `SUPERSEDED` rows, anything in Downloads. Do not edit, extend, rebuild or re-fetch data on your own initiative. If the approved data is stale for your test, a file you need is missing or `PENDING`, or anything is unclear, **stop and ask Manu**; do not work around it. Run `python data/check_approved_data.py` before a test's Step 1 and at the top of its `run.sh`; a non-zero exit means stop and ask. Manu approves every refresh himself; once he has, an agent updates `APPROVED_DATA.md` by the procedure at its bottom. Completed tests stay pinned to the files in their own `inputs.csv`.
- **Tests:** `AA/tests/T<NN>/`. Code lives in `AA/analysis/`. A test's evidence lives in its own `evidence/<run>/`.
- **Every test keeps its plan (standing rule, 2026-11-06).** When a plan for a test is written or approved, copy it verbatim to `AA/tests/T<NN>/PLAN.md` before writing any engine code. Plan mode saves plans under `C:\Users\manur\.claude\plans\` (random file names), so find the file by its title (`Grep` the title in that folder) and copy it with `Copy-Item`; create the test folder if it is missing; never retype the plan and never overwrite an existing `PLAN.md` (a revised plan goes beside it as `PLAN_v2.md`). `PLAN.md` is the implementation plan; the frozen design is `T<NN>.md` §1-§3, and it wins where they differ. Say in the hand-over message that the copy was made. Back-filled 2026-11-06: T03, T04, T05. AGENT.md task 3 has the general rule.
- **Earlier studies** (`AA/analysis/evidence/{main,segment_v1,segment_v2,why_n100sc100,final_strategy}`) predate this layout. Each has a METHODS.md, but none has a pre-registration or a finding ID.

- **Every test's write-up and results page** follow AGENT.md rule 10 and R10: a plain-words walkthrough (§3), one backtest end to end with formulas and real numbers (inputs → signal → trade → units → daily value → equity curve → statistics → one null draw → ranking), and a start and end date on every number and curve.
- **Cash convention (F-AA-D05):** LBES adjusted level, as-of on NSE sessions; past the file's last date, accrue at the trailing 90-session rate and count those days.
- **Extending the cash files (F-AA-D13, 2026-11-05):** `python data/extend_liquid.py` appends LIQUIDCASE returns from Postgres (`merged_historical_data_with_rics`) as `level[t] = level[t-1] * (1 + r[t])` on NSE sessions, to `Historical Data/LBES_Adjusted_Price_data_extended_<date>.csv` and `liquidEtfFinal_extended_<date>.csv`; originals are never edited, and `--check` writes nothing. LIQUIDCASE is not LIQUIDBEES: over 2024-01-24 → 2026-08-07 it compounded 5.72%/yr against LBES's 5.17%, so the extension runs about 0.5 pp/yr rich. The first appended LBES row chains from the Sunday 2026-08-09 level, so about 2 days of weekend accrual are counted twice (≤0.02%). The extended files are not yet wired into any test or review; the provenance gap F-AA-D09 for the original LBES file is still open.
- **Refreshing the data pool: only with Manu's approval (standing rule 2026-11-06, revised the same day).** An agent does not extend a file on its own initiative. If a file you need ends before the test needs it (compare its through-date in `data/APPROVED_DATA.md` with the window), stop and tell Manu. When Manu asks for a refresh, compare the file's last date with Postgres (`windmill`, read-only, creds `PG_PRICE_*` in `../wm-aiReports/.env`) and extend it *in the F-AA-D13 manner* below. The result is a **candidate**: it stays off-limits until Manu approves it and `APPROVED_DATA.md` is updated (its procedure checks only the new rows, in the context of the approved history). Say so in the write-up. The manner: (1) same source and adjustment basis as the file being extended (Eikon `ohlcv_eikon` for Eikon files, never the unadjusted Kite `merged_historical_data_with_rics` unless the file is itself Kite or LIQUIDCASE); (2) read-only session; (3) rows already in the file are copied verbatim, the original is never edited, and the output is a new file `<name>_extended_<last session>.<ext>` (R6 sha256s stay valid); (4) stop if the overlap disagrees (Eikon is re-adjusted for corporate actions now and then; the DB keeps `*_bkp_ca_<date>` tables), and print every date that is in one side only; (5) a `--check` flag that writes nothing; (6) log it here.
